# QA 테스트 하는 법

내가 만든 웹사이트가 제대로 작동하는지 직접 써보면서 확인하는 과정입니다.

---

## 주의사항

**테스트하는 동안에는 코드를 수정하지 마세요.**

체크리스트를 채우면서 FAIL이 나와도, 일단 끝까지 테스트를 진행하세요. 코드 수정은 **테스트가 전부 끝나고, 종료 시간을 기록한 다음에** 합니다.

순서: 테스트 전부 완료 -> 종료 시간 기록 -> 제출 요약 작성 -> 커밋 -> 그 다음에 코드 수정

테스트 도중에 코드를 고치면 어디까지가 원래 결과이고 어디부터가 수정 후 결과인지 구분이 안 됩니다.

## 1단계. QA 폴더를 내 프로젝트에 넣기

### 1-1. zip 파일 다운로드

Slack 자료공유 채널에서 `QA.zip` 파일을 다운로드하세요.

### 1-2. 압축 풀기

다운로드한 `QA.zip`을 더블클릭하면 `QA` 폴더가 나옵니다.
이 안에 두 파일이 있습니다:

```
QA/
  QA_HOW_TO.md         <- 지금 읽고 있는 이 파일
  MP1_QA_CHECKLIST.md  <- 테스트 체크리스트 (이걸 채워야 합니다)
```

### 1-3. 내 프로젝트 폴더에 넣기

`QA` 폴더를 통째로 **내 프로젝트 폴더 안**에 넣으세요. `index.html`이 있는 그 폴더입니다.

```
내 프로젝트 폴더/
  index.html       <- 이미 있는 파일
  script.js        <- 이미 있는 파일
  style.css        <- 이미 있는 파일
  admin/           <- 이미 있는 폴더
  QA/              <- 여기에 넣으세요
    QA_HOW_TO.md
    MP1_QA_CHECKLIST.md
```

### 1-4. VS Code에서 열기

VS Code 왼쪽 파일 목록에서 `QA` 폴더를 열고, `MP1_QA_CHECKLIST.md`를 클릭하면 열립니다.


## 기능테스트와 시나리오 테스트의 차이

체크리스트에는 두 종류의 테스트가 있습니다. 하는 방식이 다릅니다.

**기능테스트 (Part A)** - 기능 하나만 따로 꺼내서 확인합니다.

- "접수 버튼을 누르면 DB에 저장되는가?" 이것만 봅니다.
- 앞뒤 맥락 없이, 그 기능 하나가 작동하는지만 확인합니다.
- PASS 또는 FAIL로 판정합니다.

**시나리오 테스트 (Part B)** - 실제 사용자가 처음부터 끝까지 쓰는 흐름을 따라갑니다.

- "62세 어르신이 링크를 받고 -> 화면을 열고 -> 자격증을 찾고 -> 이름을 쓰고 -> 접수 버튼을 누른다"
- 이 흐름 중에 **어디서 막히는지, 어디서 해매는지**를 찾습니다.
- PASS/FAIL이 아니라 **"막힌 곳"**을 적습니다.

쉽게 말하면:
- 기능테스트 = "이 버튼 누르면 되나?" (기능이 주어)
- 시나리오 테스트 = "이 사람이 쓸 수 있나?" (사람이 주어)

**순서: 기능테스트(Part A)를 먼저 하고, 시나리오 테스트(Part B)를 나중에 하세요.** 기능이 안 되면 시나리오를 돌려도 의미가 없습니다.

---

## 3단계. 기능테스트 하기 (Part A)

### 체크리스트 읽는 법

파일 안에 이런 줄이 많이 있습니다:

```
- [ ] **M1.** 배포 주소가 열린다 - Vercel 주소를 시크릿 창에서 열었을 때 접수 화면이 뜬다
```

이 한 줄이 **테스트 항목 1개**입니다. 하나씩 직접 해보고 결과를 적습니다.

### 기능테스트 하나를 하는 순서

**M1번을 예로 들겠습니다.**

항목: `배포 주소가 열린다 - Vercel 주소를 시크릿 창에서 열었을 때 접수 화면이 뜬다`

**(1) 읽기** - 뭘 하라는 건지 먼저 읽습니다.
- "Vercel 주소를 시크릿 창에서 연다"

**(2) 하기** - 그대로 합니다.
- Chrome에서 `Ctrl + Shift + N` (Mac은 `Cmd + Shift + N`)을 눌러 시크릿 창을 엽니다
- 주소창에 내 Vercel 주소를 붙여넣고 Enter를 누릅니다

**(3) 보기** - 기대한 결과가 나왔는지 봅니다.
- 접수 화면이 떴나요?

**(4) 적기** - 결과에 따라 체크합니다.

---

### 성공했을 때

접수 화면이 잘 떴으면, `[ ]` 안에 `x`를 넣으세요.

**수정 전:**
```
- [ ] **M1.** 배포 주소가 열린다
```

**수정 후:**
```
- [x] **M1.** 배포 주소가 열린다
```

`[ ]`를 `[x]`로 바꾸는 겁니다. x 앞뒤에 빈칸이 없어야 합니다.

---

### 실패했을 때

화면이 안 떴으면, 체크하지 말고 뒤에 `FAIL:`을 붙이고 **무슨 일이 일어났는지** 적으세요.

**수정 후:**
```
- [ ] **M1.** 배포 주소가 열린다 - FAIL: 404 Not Found 페이지가 뜸
```

또는:

```
- [ ] **M1.** 배포 주소가 열린다 - FAIL: 빈 화면이 뜸. 아무것도 안 보임
```

**적어야 할 것:**
- 화면에 무엇이 보였는지 (빈 화면, 에러 메시지, 404, 글자만 나옴 등)
- 에러 표시가 있으면 그 내용
- 버튼을 눌렀는데 반응이 없었다면 그 상황

### Part A를 M1부터 순서대로 끝까지 하세요.

## 4단계. 시나리오 테스트 하기 (Part B)

기능테스트를 끝낸 뒤에 하세요.

시나리오 테스트는 기능테스트와 다릅니다. 기능이 되는지가 아니라, **실제 사용자가 쓸 수 있는지**를 봅니다.

### 시나리오 테스트 하는 법

**US1번을 예로 들겠습니다.**

```
> 김순자(62세)가 학원 직원에게 받은 링크로 요양보호사 시험을 접수합니다.
```

내가 62세 김순자라고 생각하고 처음부터 써봅니다. 이 분은:
- 컴퓨터를 잘 모릅니다
- 글씨가 작으면 안 보입니다
- "접수"가 뭔지 모를 수도 있습니다

그 눈으로 보면서, **"이 화면을 처음 보는 사람이 해맬 곳"**을 찾아 적습니다.

기능테스트에서는 "된다/안 된다"만 봤다면, 시나리오 테스트에서는 **"되긴 되는데, 이 사람이 찾을 수 있나?"**를 봅니다.

예를 들어:
- 접수 버튼은 작동한다 (기능테스트 PASS) -> 그런데 버튼이 너무 작아서 62세가 못 찾는다 (시나리오에서 "막힌 곳")
- DB 저장은 된다 (기능테스트 PASS) -> 그런데 접수 완료 안내가 없어서 됐는지 모른다 (시나리오에서 "막힌 곳")

### "막힌 곳" 적는 법

시나리오 끝에 있는 `막힌 곳:`에는 이렇게 적으세요:

```
막힌 곳: 접수 화면에서 요양보호사가 어디 있는지 3초 이상 찾았다. 카드가 8개인데 글씨가 작아서 스크롤해야 보임.
```

또는:

```
막힌 곳: 접수 버튼을 눌렀는데 아무 반응이 없어서 됐는지 안 됐는지 모르겠다.
```

막히는 곳이 없었으면:

```
막힌 곳: 없음
```

## 5단계. GitHub에 올리기

테스트를 다 했으면 QA 폴더를 GitHub에 올립니다.

### 5-1. VS Code 터미널 열기

VS Code 상단 메뉴에서 `Terminal` -> `New Terminal`을 클릭하세요.

### 5-2. 명령어 3줄 입력

터미널에 아래 명령어를 **한 줄씩** 입력하고 Enter를 누르세요.

첫 번째 줄 - QA 폴더를 등록합니다:
```bash
git add QA/
```

두 번째 줄 - 변경 사항을 저장합니다:
```bash
git commit -m "test: QA 체크리스트 결과 기록"
```

세 번째 줄 - GitHub에 올립니다:
```bash
git push
```

### 5-3. 확인

GitHub에서 내 저장소 페이지를 열어보세요. `QA` 폴더가 보이고, 안에 들어가서 `MP1_QA_CHECKLIST.md`를 클릭하면 체크박스가 체크된 상태로 보입니다.

## 자주 묻는 질문

### "PASS가 몇 개여야 하나요?"

- **Must 8개**: 전부 통과해야 합니다. 하나라도 FAIL이면 수정하세요.
- **Should 8개**: 전부 통과해야 합니다. FAIL이면 수정하세요.
- **Could 4개**: 선택입니다. 안 해도 됩니다.
- **시나리오 5개**: 3개 이상 해보세요.
- **엣지 케이스 10개**: 선택입니다. 많이 할수록 좋습니다.

### "FAIL이 나오면 고쳐야 하나요?"

Must 항목이 FAIL이면 코드를 고치고 다시 테스트하세요. 고친 뒤에 `[x]`로 바꾸고 뒤에 `(수정 후 PASS)`라고 적으면 됩니다.

```
- [x] **M3.** 접수 폼 제출 - FAIL: 버튼 클릭 시 에러 -> script.js 15줄 오타 수정 (수정 후 PASS)
```

Should 항목도 오늘 통과해야 합니다. 수정 후 다시 테스트하세요.

### "시크릿 창이 뭔가요?"

내 브라우저에 저장된 정보(로그인, 캐시)를 안 쓰는 깨끗한 창입니다. 다른 사람이 내 사이트를 처음 열었을 때와 같은 상태입니다. `Ctrl + Shift + N` (Mac은 `Cmd + Shift + N`)으로 열 수 있습니다.

### "Supabase Table Editor는 어디서 열어요?"

1. supabase.com에 로그인합니다
2. 내 프로젝트를 클릭합니다
3. 왼쪽 메뉴에서 **Table Editor**를 클릭합니다
4. 테이블 이름(national_applications 등)을 클릭하면 데이터가 보입니다

### "git push에서 에러가 나요"

`error: failed to push` 메시지가 나오면:

```bash
git pull --rebase
git push
```

이 두 줄을 차례로 입력해보세요.

## 테스트가 끝나면

1. `MP1_QA_CHECKLIST.md` 맨 위의 `테스트 종료: __:__`에 시간을 적으세요
2. 맨 아래 제출 요약을 채우세요:

```
[Part A 기능테스트]
Must:      ___/8 PASS  (필수)
Should:    ___/8 PASS  (필수)
Could:     ___/4 PASS  (선택)

[Part B 시나리오 테스트]
시나리오:  ___/5 완주  (3개 이상 필수)
엣지:      ___/10 기록 (선택)
```

3. 다시 커밋하고 푸시하세요:

```bash
git add QA/
git commit -m "test: QA 최종 결과"
git push
```

수고하셨습니다.
